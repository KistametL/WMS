JWT คืออะไร และทำงานยังไง

JWT (JSON Web Token) คือ token ที่ส่งไปพร้อมกับทุก request เพื่อบอกว่า "ฉันคือใคร และมีสิทธิ์อะไร"

Flow การ Login และใช้งาน API: 1. Client ส่ง email + password → POST /api/v1/auth/login 2. Server ตรวจรหัสผ่าน → สร้าง JWT token ส่งกลับ 3. Client เก็บ token ไว้ 4. Client ส่ง token ทุกครั้งที่เรียก API → Header: Authorization: Bearer eyJhbGci... 5. Server ตรวจ token → รู้ว่าใคร → อนุมัติหรือปฏิเสธ

JWT แบ่งเป็น 3 ส่วน คั่นด้วยจุด header.payload.signature

ตัวอย่าง JWT (decode แล้ว) JSON 
// Header — บอกว่าใช้ algorithm อะไร
{ "alg": "HS256", "typ": "JWT" }

// Payload — ข้อมูลที่เก็บไว้ใน token (ทุกคนอ่านได้!)
{
  "user_id":     "773b1f73-0c91-4b47-...",
  "email":       "admin@wms.com",
  "roles":       ["super_admin"],
  "permissions": ["products.read", "orders.write"],
  "exp":         1779395488,   // หมดอายุ
  "iat":         1779309088    // สร้างเมื่อ
}

// Signature — ใช้ตรวจว่า token ไม่ถูกแก้ไข
HMAC-SHA256(base64(header) + "." + base64(payload), JWT_SECRET)
⚠ สำคัญ

Payload ถูก Base64 encode ไว้ ไม่ใช่ encrypt — ใครก็ decode อ่านได้ อย่าเก็บข้อมูลลับใน JWT เด็ดขาด (เช่น password, credit card). สิ่งที่ปลอดภัยคือ signature ที่ certify ว่า token ไม่ถูกแก้ไข

Middleware Flow

Middleware คือ code ที่รันก่อน handler จริง — เหมือนด่านตรวจก่อนเข้าห้อง ถ้าไม่ผ่าน ตอบ error กลับทันที ไม่ให้เข้าถึง handler

Request lifecycle: HTTP Request │ ▼ RequireAuth ← ตรวจ JWT token │ ✓ valid ▼ RequirePermission ← ตรวจว่ามี permission นี้ไหม (optional) │ ✓ has permission ▼ Handler ← logic จริงๆ │ ▼ HTTP Response ถ้าด่านไหนล้มเหลว → หยุดทันที ไม่ไปต่อ: RequireAuth fail → 401 Unauthorized RequirePermission fail → 403 Forbidden
ทำไมต้องแยกเป็น middleware แทนที่จะตรวจใน handler

ถ้าตรวจใน handler ทุกตัว — code ซ้ำ 50 จุด ลืมได้ทุกเมื่อ
ถ้าเป็น middleware — ใส่ที่เดียว ครอบทุก route อัตโนมัติ ลืมไม่ได้

RequireAuth — ตรวจ JWT Token

Middleware ตัวแรก ทุก protected route ต้องผ่านตัวนี้ก่อนเสมอ

สิ่งที่ตรวจ

  • มี Authorization header ไหม
  • รูปแบบเป็น Bearer <token> ไหม
  • Signature ถูกต้องไหม (token ไม่ถูกแก้ไข)
  • Algorithm เป็น HS256 ไหม (ป้องกัน algorithm confusion attack)
  • Token ยังไม่หมดอายุไหม
internal/middleware/auth.go GO 
func RequireAuth(cfg *config.Config) gin.HandlerFunc {
    return func(c *gin.Context) {
        authHeader := c.GetHeader("Authorization")
        if authHeader == "" {
            response.Unauthorized(c, "authorization header is required")
            c.Abort()  // หยุด ไม่ไปต่อ
            return
        }

        parts := strings.SplitN(authHeader, " ", 2)
        if len(parts) != 2 || !strings.EqualFold(parts[0], "Bearer") {
            response.Unauthorized(c, "format must be: Bearer <token>")
            c.Abort()
            return
        }

        token, err := jwt.Parse(parts[1], func(t *jwt.Token) (interface{}, error) {
            // ป้องกัน algorithm confusion attack
            // ถ้า attacker ส่ง alg: "none" มา ต้อง reject ทันที
            if _, ok := t.Method.(*jwt.SigningMethodHMAC); !ok {
                return nil, jwt.ErrSignatureInvalid
            }
            return []byte(cfg.JWT.Secret), nil
        }, jwt.WithValidMethods([]string{"HS256"}))

        if err != nil || !token.Valid {
            response.Unauthorized(c, "invalid or expired token")
            c.Abort()
            return
        }

        claims := token.Claims.(jwt.MapClaims)
        c.Set("wms.user_id", claims["user_id"])
        c.Set("wms.roles", claims["roles"])
        c.Set("wms.permissions", claims["permissions"])

        c.Next()  // ผ่าน ไปต่อ
    }
}
Context Key Prefix

ใช้ prefix "wms." เพราะ gin.Context ใช้ string เป็น key — ถ้าไม่มี prefix อาจชนกับ key ของ library อื่นที่ใช้ใน middleware ตัวเดียวกัน

RequirePermission — ตรวจสิทธิ์ละเอียด

ใช้เมื่อ route ต้องการ permission เฉพาะ เช่น products.read, orders.write

Permission ที่มีในระบบ (12 อัน)

Permission ความหมาย ใครมี
products.readดูสินค้าทุก role ยกเว้น viewer
products.writeเพิ่ม/แก้ไขสินค้าadmin, manager
inventory.readดู stockทุก role
inventory.writeรับ/จ่ายสินค้าwarehouse_staff+
orders.readดู orderทุก role
orders.writeสร้าง/แก้ orderfulfillment_staff+
orders.fulfillจัดส่ง/ปิด orderfulfillment_staff+

internal/middleware/auth.go GO 
// ผ่านถ้า user มี permission อย่างน้อย 1 อัน จาก list ที่กำหนด
func RequirePermission(permissions ...string) gin.HandlerFunc {
    return func(c *gin.Context) {
        userPerms := getStringSlice(c, "wms.permissions")

        for _, required := range permissions {
            for _, has := range userPerms {
                if has == required {
                    c.Next()  // พบ permission → ผ่าน
                    return
                }
            }
        }

        response.Forbidden(c, "you do not have permission to perform this action")
        c.Abort()
    }
}

RequireRole — ตรวจ Role

ใช้เมื่อ route ต้องการ role เฉพาะ เช่น admin-only settings page

5 Roles ในระบบ

super_admin

เจ้าของระบบ ทำได้ทุกอย่าง ไม่มีข้อยกเว้น

admin

ผู้จัดการระบบ จัดการ user และ settings ได้ ยกเว้น system-level

manager

ดู report ได้ทุกอย่าง แก้ไขข้อมูลหลักได้ แต่ไม่จัดการ user

warehouse_staff

รับของเข้า จ่ายของออก ดู stock ดู order ไม่จัดการ settings

fulfillment_staff

จัดส่ง order ใช้ POS รับของได้ แต่ไม่แก้ข้อมูลสินค้า

internal/middleware/auth.go GO 
func RequireRole(roles ...string) gin.HandlerFunc {
    return func(c *gin.Context) {
        userRoles := getStringSlice(c, "wms.roles")

        for _, required := range roles {
            for _, has := range userRoles {
                if has == required {
                    c.Next()
                    return
                }
            }
        }

        response.Forbidden(c, "insufficient role to access this resource")
        c.Abort()
    }
}

Helper Functions

ดึงข้อมูล user จาก context ใน handler โดยไม่ต้อง type-cast เอง

ใช้ใน handler ไหนก็ได้ GO 
userID  := middleware.GetUserID(c)      // "773b1f73-..."
email   := middleware.GetEmail(c)       // "admin@wms.com"
roles   := middleware.GetRoles(c)       // ["super_admin"]
perms   := middleware.GetPermissions(c) // ["products.read", ...]

// ตรวจ permission ภายใน handler (ไม่ block route)
if middleware.HasPermission(c, "reports.view") {
    // แสดงข้อมูลพิเศษ
}
ทำไมต้องมี Helper?

JWT decode arrays เป็น []interface{} ไม่ใช่ []string — helper ทำการแปลงให้อัตโนมัติ ถ้าไม่มี helper ต้อง type-cast เองทุก handler ซึ่งเสี่ยง panic ถ้าทำผิด

Pattern การใช้งานใน main.go

cmd/api/main.go — วิธีลงทะเบียน routes GO 
api := r.Group("/api/v1")

// ── Public routes (ไม่ต้อง login) ──────────────
authHandler.RegisterRoutes(api)      // POST /auth/login, /auth/refresh

// ── Protected routes (ต้อง login ทุก request) ──
protected := api.Group("")
protected.Use(middleware.RequireAuth(cfg))
{
    // ทุก role เข้าได้ (แค่ต้อง login)
    protected.GET("/me", handler.Me)

    // ต้องมี permission products.read
    protected.GET("/products",
        middleware.RequirePermission("products.read"),
        productHandler.List)

    // ต้องมี permission products.write
    protected.POST("/products",
        middleware.RequirePermission("products.write"),
        productHandler.Create)

    // ── Admin-only area ─────────────────────────
    admin := protected.Group("/admin")
    admin.Use(middleware.RequireRole("super_admin", "admin"))
    {
        admin.GET("/users", userHandler.List)
        admin.POST("/users", userHandler.Create)
    }
}

CI คืออะไร และทำไมต้องมี

CI (Continuous Integration) คือระบบที่รัน test อัตโนมัติทุกครั้งที่ push code — ป้องกันไม่ให้ code เสียหายเข้า main branch

ถ้าไม่มี CI: push code → merge → deploy → bug ใน production ← ค้นหายาก แก้เร่งด่วน เสียเวลา ถ้ามี CI: push code → CI รัน test → fail → แจ้ง dev ↓ pass → merge ได้ → deploy ปลอดภัย

ปัญหา CI เดิมและสิ่งที่แก้

CI เดิมปัญหาแก้เป็น
go vet ตรวจแค่ syntax พื้นฐาน ไม่จับ error ที่ลืม check, security hole golangci-lint (100+ linters)
job เดียว sequential lint fail → ไม่รู้ว่า test ผ่านหรือเปล่า 2 jobs parallel (lint + test)
go test ./... ไม่จับ race condition (goroutine bug) go test -race ./...
trigger ทุก file แก้ docs/ ก็เปลือง CI minutes ฟรี paths: backend/**
ไม่มี concurrency push 3 ครั้ง = CI 3 อันทำงานซ้อนกัน cancel-in-progress: true

golangci-lint คืออะไร

เครื่องมือมาตรฐาน Go ที่รวม linter หลายตัวไว้ด้วยกัน รันครั้งเดียวตรวจหลายอย่างพร้อมกัน

Linters ที่เปิดไว้ในโปรเจคนี้

Linterจับอะไรตัวอย่าง bug
errcheck ลืม check error return os.Remove(file) โดยไม่ check err
staticcheck Advanced analysis (รวม gosimple) ใช้ loop copy แทน copy(), dead code
govet Suspicious constructs printf format ไม่ตรงกับ argument
unused Code ที่ไม่ถูกใช้ function ที่ declare แต่ไม่เรียก
gosec Security issues Hardcoded credentials, SQL injection risk
gofmt / goimports Format + import grouping Import ไม่จัดกลุ่ม stdlib vs third-party
backend/.golangci.yml YAML 
version: "2"

linters:
  default: none
  enable:
    - errcheck
    - govet
    - ineffassign
    - staticcheck    # รวม gosimple แล้วใน v2
    - unused
    - gosec

  settings:
    gosec:
      excludes:
        - G114       # timeout จัดการใน app code เอง

  exclusions:
    paths:
      - internal/database/generated  # sqlc generated — ไม่ตรวจ

formatters:
  enable:
    - gofmt
    - goimports
⚠ golangci-lint v1 vs v2

ใช้ golangci-lint-action@v7 เพื่อรองรับ v2 (v6 รองรับแค่ v1)
Pin version ตรงๆ เสมอ: version: v2.12.2 อย่าใช้ latest เพราะ action อาจ resolve ผิด version

CI Pipeline สุดท้าย

.github/workflows/ci.yml YAML 
name: CI

on:
  pull_request:
    branches: [main, develop]
    paths:
      - "backend/**"         # ✓ รันแค่ตอน backend เปลี่ยน
      - ".github/workflows/ci.yml"
  push:
    branches: [develop]
    paths:
      - "backend/**"
      - ".github/workflows/ci.yml"

# push ใหม่มา → cancel run เก่าทิ้ง
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

jobs:
  # รัน parallel — รู้ชัดว่า lint fail หรือ test fail
  lint:
    name: Lint
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version: "1.25"
          cache-dependency-path: backend/go.sum
      - uses: golangci/golangci-lint-action@v7  # v7 รองรับ lint v2
        with:
          version: v2.12.2                      # pin ตรงๆ
          working-directory: backend

  test:
    name: Test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version: "1.25"
          cache-dependency-path: backend/go.sum
      - name: Build
        working-directory: backend
        run: go build ./...
      - name: Test
        working-directory: backend
        run: go test -race -coverprofile=coverage.out ./...
      - name: Coverage report
        working-directory: backend
        run: go tool cover -func=coverage.out

ผลที่ได้

  • lint + test รัน parallel ประหยัดเวลา
  • จับ error ที่ go vet ตรวจไม่เจอ
  • จับ race condition ด้วย -race flag
  • เห็น test coverage % ทุก push
  • ไม่เปลืองเวลาตอนแก้แค่ docs
  • push เร็วๆ หลายครั้ง → cancel อันเก่า รันแค่อันล่าสุด
